# WhatsApp service job alerts

Service jobs use Meta’s WhatsApp Cloud API. The integration sends an approved utility template to every eligible service provider, receives button replies and delivery statuses through a webhook, and supports free-form replies inside the 24-hour customer-service window.

## Prerequisites

- Existing VHH Fleet Meta app and WhatsApp Business Account (the same app as the earlier API demo).
- A production sender phone number ID and a permanent system-user access token with WhatsApp messaging permission.
- The Meta app secret and a webhook verify token.
- Business verification, an approved display name and a payment method on the WhatsApp account.
- The utility template below approved in the selected language.
- Provider WhatsApp numbers opted in to receive job alerts.

The temporary demo token and `vhh_api_test` template are for the demo script only. Do not use them for production job alerts.

## Configuration

Set in the root `.env` (server-only; never in the web or mobile bundle):

| Variable | Purpose |
| --- | --- |
| `SERVICE_JOB_ALERTS_ENABLED` | `true` only after template approval and provider onboarding |
| `SERVICE_JOB_LINK_SECRET` | 32+ byte HMAC key for provider links; generated by deployment |
| `META_WHATSAPP_ACCESS_TOKEN` | Permanent Meta system-user access token |
| `META_WHATSAPP_PHONE_NUMBER_ID` | Production sender phone number ID |
| `META_WHATSAPP_BUSINESS_ACCOUNT_ID` | WABA ID used to validate webhook entries |
| `META_WHATSAPP_APP_SECRET` | Meta app secret used for webhook signatures |
| `META_WHATSAPP_WEBHOOK_VERIFY_TOKEN` | Random token entered in the Meta webhook configuration |
| `META_WHATSAPP_JOB_TEMPLATE` | `vhh_service_job_alert` |
| `META_WHATSAPP_TEMPLATE_LANGUAGE` | `en_US` (or the approved language) |
| `META_WHATSAPP_API_VERSION` | Graph API version, default `v25.0` |
| `META_WHATSAPP_GRAPH_URL` | Default `https://graph.facebook.com`; local fake server in tests |
| `FLEET_CONTACT_PHONE` | Optional office phone shown on the provider page |

Environment changes require an API restart. Alerts can be disabled at any time without affecting job creation.

## Linked-phone demo

For a demo with a dedicated WhatsApp phone, start the optional
`deploy/compose.demo-openwa.yaml` overlay alongside the Fleet deployment.
Set `OPENWA_DEMO_MASTER_KEY` and `OPENWA_DEMO_KEY_PEPPER` to independent random
secrets in the root environment. The gateway dashboard listens on the server's
loopback port 12785. Use an SSH tunnel to create a session and scan its QR code
under **Linked devices** on the demo phone.

Create an operator key restricted to that session and the consenting providers'
individual chat IDs. Set `OPENWA_DEMO_URL=http://openwa-demo:2785`,
`OPENWA_DEMO_SESSION_ID` and `OPENWA_DEMO_API_KEY`. Set `OPENWA_DEMO_SENDER` to
the linked phone number and `OPENWA_DEMO_RECIPIENTS` to the comma-separated
provider numbers with country codes. Fleet excludes the linked number. When the session reports
`ready`, set `SERVICE_JOB_ALERT_TRANSPORT=openwa-demo` and
`SERVICE_JOB_ALERTS_ENABLED=true` and recreate the Fleet app container.

Each eligible provider receives a text with the breakdown details and their
signed link to accept, decline or complete the job. Fleet records gateway
acceptance as **Sent**. The demo supports provider actions through the link.
Set the transport to `meta` to use the approved Cloud API template again.

## Meta template

Submit [the ready-to-use template definition](../deploy/whatsapp/vhh_service_job_alert.en_US.json) through WhatsApp Manager or the [Meta message templates endpoint](https://developers.facebook.com/docs/graph-api/reference/whats-app-business-account/message_templates/). Select **Utility**, English (US), and name it `vhh_service_job_alert`. Enable alerts after Meta approves it. The URL prefix must match the public Fleet host.

Header:

```text
Service request
```

Body:

```text
VHH Fleet service request {{1}}
Vehicle: {{2}} ({{3}})
Issue: {{4}}
Location: {{5}}

Tap Accept job to take this request, or View job for details.
```

Footer:

```text
First provider to accept is assigned.
```

Buttons, in order:

| Index | Type | Text | Destination / payload |
| --- | --- | --- | --- |
| 0 | Quick reply | `Accept job` | Returns `accept_job` to the webhook |
| 1 | Quick reply | `Can't take` | Returns `cant_take` to the webhook |
| 2 | URL | `View job` | `https://fleet.nativesounds.co.za/j/{{1}}` |

Example values for approval:

| Variable | Example |
| --- | --- |
| `{{1}}` | `SJ-001042` |
| `{{2}}` | `GP 24 VH GP` |
| `{{3}}` | `VHH-012` |
| `{{4}}` | `Mechanical: Engine overheating, truck stopped` |
| `{{5}}` | `N1 North, near Polokwane` |
| URL variable | `7f3c2a...` |

Template parameters are clipped, newlines are collapsed and URLs are removed from body placeholders. Missing location becomes `Shared on the job page`. Changing the approved copy requires a new template name/version and an environment update.

## Webhook

Configure the public callback URL (Fleet’s gateway forwards it to Fastify):

```text
https://fleet.nativesounds.co.za/api/whatsapp/webhook
```

Subscribe to the `messages` field. The app handles:

- **GET** verification with `hub.mode=subscribe`, `hub.verify_token` and `hub.challenge`.
- **POST** events with `X-Hub-Signature-256` HMAC-SHA256 verification over the raw request body using `META_WHATSAPP_APP_SECRET`; unsigned/tampered requests are rejected.
- If `META_WHATSAPP_BUSINESS_ACCOUNT_ID` is set, events for other accounts are ignored.
- Template quick replies: maps `context.id` (the original alert message ID) to the offer, verifies the sender number belongs to the provider, and accepts or declines.
- Interactive replies: custom IDs `offer:<offerId>:en_route`, `offer:<offerId>:arrived`, `offer:<offerId>:working` and `offer:<offerId>:complete`.
- Text replies: STOP/UNSUBSCRIBE opt-out, ACCEPT/DECLINE when exactly one offer is open, DONE/COMPLETE to start completion for a single assigned job, and a short instruction for anything else.
- Delivery statuses: sent, delivered, read and failed with error code/title; status never regresses an accepted/declined offer.
- Duplicate message IDs are idempotent. Invalid signatures return 403; real processing failures return 500 so Meta retries.

The webhook stores inbound/outbound message metadata in `whatsapp_messages`. It does not store message bodies, provider links or tokens in that table.

## Replies and the 24-hour window

The initial job alert is a template and can be sent outside the 24-hour window. Replies and progress buttons are free-form interactive messages and are only sent immediately after the provider messages the business, inside the customer-service window. The web link always works independently.

- Accept: confirmation with the signed job link and **On my way**, **Arrived**, **Working** buttons.
- Decline: thank-you and the job remains open for another provider.
- Progress: confirmation and buttons for the remaining stages and **Complete job**.
- Completion: tap **Complete job** or send `DONE` or `COMPLETE`. Reply with a short note about the work. To include up to three photos or a charge, send the photos or a message such as `AMOUNT 1500.00` before the note. Send `SKIP PHOTOS` to remove any pending photos. The note completes the job and Fleet confirms in chat. When several jobs are in progress, tap the button for the job and reply directly to its completion message.
- Fallback: Fleet includes the signed **Complete on web** link in the note prompt. The chat request expires after 30 minutes. Fleet sends one reminder with the link if the provider has not completed it and WhatsApp still permits a reply. After the service window closes, use the existing link or message Fleet to get it again. The chat state survives an API restart.
- Completion from WhatsApp and the web uses the same job record, evidence rules and audit timeline. The office sees the actor and channel alongside the note, photos and amount.
- Opt-out: confirmation and alerts disabled; re-enabling requires new consent in Fleet.

## Meta setup checklist

1. Approve `vhh_service_job_alert`.
2. Create/copy the production sender and a permanent system-user token.
3. Set the app secret and webhook verify token in `/opt/fleet/.env`.
4. Add the callback URL and subscribe to `messages`.
5. Add test provider numbers to the Meta test recipient allowlist until the sender is live.
6. Create a test service job for an internal number, check delivery/buttons/link and receive the webhook events.
7. Add the real providers and enable `SERVICE_JOB_ALERTS_ENABLED=true`.
8. Monitor offer failures in the job detail and WhatsApp quality/throughput in Meta Business Manager.

## Common Meta errors

| Code | Meaning | Action |
| --- | --- | --- |
| 190 | Access token invalid/expired | Replace the permanent token |
| 131030 | Recipient not in the allowed test list | Add the number or move to the live sender |
| 131042 | WhatsApp account payment issue | Fix the payment method in Meta Business Suite |
| 131047 | Re-engagement/24-hour-window issue | Use the approved template for the initial alert |
| 132001 | Template does not exist/not approved in this language | Check the template name, language and approval |
| 132000 | Template paused/rejected | Check template quality/status |
| 131026 | Recipient cannot receive the message | Check the number and WhatsApp status |

The job detail shows the error code and title for each failed offer. Resend after fixing the configuration. Ambiguous network outcomes are not automatically retried, to avoid duplicate alerts.

## Local testing

The stack tests run a local fake Graph server and submit signed webhook requests; they never call Meta. `SERVICE_JOB_ALERTS_ENABLED=true` with fake credentials and `META_WHATSAPP_GRAPH_URL` pointed at the fake server exercises the full queue and webhook path.

Use the old demo script only for the separate API demo described in [whatsapp-cloud-api-demo.md](whatsapp-cloud-api-demo.md).
